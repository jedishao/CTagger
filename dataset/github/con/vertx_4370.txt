Timers can fail to fire due to netty emitting trigger before timer is added to timeouts
### Version

4.1.2 & 4.2.7

### Context
We were seeing intermittent failures in our build pipelines upon investigation we suspected that timers might not be firing.

We suspected that timers that we were setting were actually failing to fire. In our debug we could see that the timer was in the timeouts field but it would never fire.

This is how it looks like:
![img](https://user-images.githubusercontent.com/6605129/167875050-11d8a5c7-9a01-4b6f-b838-8545d4cb6e5a.png)

Upon looking at the code
```java

 InternalTimerHandler(long timerID, Handler<Long> runnable, boolean periodic, long delay, ContextInternal context) {
      this.context = context;
      this.timerID = timerID;
      this.handler = runnable;
      this.periodic = periodic;
      EventLoop el = context.nettyEventLoop();
      if (periodic) {
        future = el.scheduleAtFixedRate(this, delay, delay, TimeUnit.MILLISECONDS);
      } else {
        future = el.schedule(this, delay, TimeUnit.MILLISECONDS);
      }
    }

    @Override
    public void run() {
      context.emit(this);
    }

    public void handle(Void v) {
      if (periodic) {
        if (timeouts.containsKey(timerID)) {
          handler.handle(timerID);
        }
      } else if (timeouts.remove(timerID) != null) {
        try {
          handler.handle(timerID);
        } finally {
          // Clean up after it's fired
          context.removeCloseHook(this);
        }
      }
    }

```

The netty scheduled task is added in the constructor of the `VertxImpl.InternalTimerHandler` and when
netty fires `handle(Void v)` is run where we try to remove the timer from `VertxImpl.timeouts`.  Thus a timer is expected 
to be in the map when the netty has fired.

This creates a race with `VertxImpl.scheduleTimeout()` where the timer is added to the `timeouts` map.


### Do you have a reproducer?

I have been unable to reproduce this in a project without our proprietary code.



### Extra

I will be attaching a PR wich fixes the problem for us. In this version we add the `InternalTimeHandler` instance to the map _before_ setting the netty scheduler.

In this implementation it could be possible that we might try to cancel a timer before the netty `future` has been initialized in the constructor.
We do not think this is a problem because a timer would be cancelled by an external client by the `timerID`. This is generated and returned by
`VertxImpl.scheduleTimeout()` where the constructor of `InternalTimerHandler` is called. This ensures that the constructor has fully run before the
timerID becomes known.
