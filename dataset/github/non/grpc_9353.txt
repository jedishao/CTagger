Provide a way to configure reconnection backoff parameters.
<!-- Please answer these questions before submitting a feature request. -->

### Is your feature request related to a problem?
<!-- A clear and concise description of what the problem is. Ex. I'm always frustrated when [...] -->
There is no way to configure [reconnection backoff](https://github.com/grpc/grpc/blob/master/doc/connection-backoff.md) parameters (eg, INITIAL_BACKOFF, MULTIPLIER, MAX_BACKOFF) from Java.

### Describe the solution you'd like
<!-- A clear and concise description of what you want to happen. -->
A way to configure reconnection backoff parameters.

### Describe alternatives you've considered
<!-- A clear and concise description of any alternative solutions or features you've considered. -->
I haven't found an alternative to create a policy with different parameters that applies to channel reconnection.

### Additional context
<!-- Add any other context about the feature request here. -->
Service configuration settings can be provided for a channel builder via calling `defaultServiceConfig`; the service configuration may include a retryPolicy definition (*).  This policy does not apply on subchannel reconnection; as far as I can tell, it would only apply for UNAVAILABLE status coming from the server itself, and not for UNAVAILABLE coming from when the server is down.  

It is possible (necessary) to set "waitForReady" in the service configuration setting to prevent an RPC from failing right away if the channel is not READY, and instead wait for it to be reconnected [EDIT: this is not strictly accurate, I should have said "if the channel is in TRANSIENT_FAILURE"; RPCs will not fail right away for IDLE and CONNECTING states; thanks to Eric for pointing that out in a comment below].

That, together with a deadline (either specific to the RPC call point in the code or given as a timeout in the service config for the method) can be used, but overall the exponential backoff parameters for the retry policy for reconnections can't be configured, while the retry policy for `UNAVAILABLE` answers from the server can be configured in the service config itself.  My understanding of that being the case comes from:

* The code in `ManagedChannelImplBuilder` creates a new instance of an `ExponentialBackoffPolicy.Provider`
https://github.com/grpc/grpc-java/blob/3500243f4320fcde1d567184b822c98de017498e/core/src/main/java/io/grpc/internal/ManagedChannelImplBuilder.java#L627
* `ExponentialBackoffPolicy` has default values matching the values documented in `connection-backoff.md`.
* While the `ExponentialBackoffPolicy` has setter methods, they are package private and they are not used from anywhere in the code.

--
(*) Note the method retry policy defined in a service configuration and the retry policy for reconnections specified in [reconnection backoff](https://github.com/grpc/grpc/blob/master/doc/connection-backoff.md), despite having similar parameters for initial, multiplier and max, do not specify the same behavior: the value `v` implied by the service configuration defined policy is used for the upper range in a uniformly random `[0, v]` used to actually decide the retry delay (thus, for method retry policy it is possible to have a later actual retry delay /smaller/ than a previous one).  The reconnection retry policy applies a jitter according to the equations defined in its documentation [page](https://github.com/grpc/grpc/blob/master/doc/connection-backoff.md#proposed-backoff-algorithm); this jitter results in variation but not as marked as for the service configuration/method case.
