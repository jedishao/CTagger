Behavior in date_parse with %v specifier
Hi all,

I have the following simple query running on Presto:

```
SELECT date_parse('2017-01-05-31' ,'%Y-%m-%v-%d');
```
Rather than returning a date object, the following error is surfaced:
```
Cannot parse "2017-01-05-31": Value 31 for dayOfMonth must be in the range [1,29]
```

According to the [documentation for datetime functions](https://prestodb.io/docs/0.217/functions/datetime.html), it notes the following definition for `%v`:

`Week (01 .. 53), where Monday is the first day of the week; used with %x`

Corresponding definition for `%x`:

`Year for the week, where Monday is the first day of the week, numeric, four digits; used with %v`
 
In the Presto tests, [this is the only case I could find](https://github.com/prestodb/presto/blob/master/presto-main/src/test/java/com/facebook/presto/operator/scalar/TestDateTimeFunctionsBase.java#L855-L857) where the `%v` date format is tested, and it is tested only with `%x`, where it correctly returns the Monday associated with that date/year.

Should Presto support the mixing of the `%v` specifier with other specifiers other than `%x`? If so, then there seem to be edge cases where it does not perform correctly. If not, should the documentation be updated to more explicitly note the limitations of the specifiers? In the below section, I provide some sample queries that show interesting behavior.

---

Here is some additional information I found while just doing some surface investigation:

A test just like the one we have in our testing file:
Query: `SELECT date_parse('2017 05' ,'%Y %v')`
Result (Correct): `2017-01-30 00:00:00.000`.

In case month is being treated as zero-indexed (as the range [1,29] suggests February), I tried this: 
Query: `SELECT date_parse('2017-00-05-31' ,'%Y-%m-%v-%d')`.
Result (Failed): `"Cannot parse "2017-00-05-31": Value 0 for monthOfYear must be in the range [1,12]"`. So it isn't zero-indexing the month, although maybe it is zero-indexing it later and getting confused.

If we change the value for the `%v` specifier to something else, like 1, we get this behavior:
Query: `SELECT date_parse('2017-01-01-30' ,'%Y-%m-%v-%d');`
Result (Undefined?): `2017-01-30 00:00:00.000`
So despite January 30 2017 not being in the first week of the year, it returned a date object for January 30 2017.

If we do something that is completely wrong, like:
Query: `SELECT date_parse('2017-01-15-30' ,'%Y-%m-%v-%d');` - meaning January 30 2017 which should fall on the 15th week of the year, we get
Result (Undefined?): `2017-04-30 00:00:00.000`

So in case 3, we provided the wrong week, and it gave a date object as if we didn't provide a week at all, and in case 4, we provided the wrong week, it gave a different date than if we had just asked for the 15th week of 2017 or for 1/30/2017.

So in sum, it seems that there is unexpected behavior in the case that we mix the week of the year specifier, `%v`, with other specifiers that are not the year.
