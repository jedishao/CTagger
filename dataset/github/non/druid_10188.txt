targetRowsPerSegment doesn't affect segment size as segments are not sub-partitioned.
### Affected Version

apache-druid-0.18.1

### Description

We are ingesting data with `DAY` as segment granularity. We chose to do `single_dim` secondary partitioning on `H3_HEX_RES_5` with a `targetRowsPerSegment` at 5,500,000 rows.

It is expected that this dataset has about 10 million rows per day, so using this `partitionsSpec` we expect each day to have 10,000,000 / 5,500,000 ~= 2 partitions. However, after ingesting the data we have one segment per day with the expected 10M rows per segment. No secondary partitioning is performed.

When we try to ingest the same dataset with `WEEK` as the segment granularity (70M rows expected) `java.lang.OutOfMemoryError: Java heap space` are raised. By analysing the heap dump we learned that it is trying to keep these entire segments in memory. Again, this is suggesting it is not using `targetRowsPerSegment` to control the segment size.

Below I have added some information on out configuration and ingestionSpec, but let me know if other materials are helpful and I will provide them.

#### Cluster Size
- Master server
  - m5.large instance: 2 vCPU, 8 GiB Memory
- Data servers
  - 2 i3.xlarge instances: 4 vCPU, 30.5 GiB Memory, 1 x 0.95TB SSD (each)
- Query server
  - m5.large instace: 2 vCPU, 8GiB Memory

#### Configurations in use
`druid.indexer.runner.javaOpts=-server -Xms8g -Xmx8g -XX:MaxDirectMemorySize=8g -Duser.timezone=UTC -Dfile.encoding=UTF-8 -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/home/ec2-user/apache-druid-0.18.1/var/heap_dumps/druid-heap.hprof -Djava.util.logging.manager=org.apache.logging.log4j.jul.LogManager`
