Cap epoch during Paxos contention on retries
Currently, we are performing catch up to the “latest existing” epoch on CMS rejections (both Paxos and non-paxos). But in some of the cases, we actually _do_ know the epoch that is highest in the log, and there is a chance there is already a debounce task that attempts to catch up to that epoch. This means that we could:


a) return Epoch alongside with [applied] value from DistributedLogKeyspace#tryCommitOne, since it is guaranteed to be the highest known epoch that can be read serially
b) return latest Epoch to the remote processor while returning rejection results, if we know we are at the latest epoch
