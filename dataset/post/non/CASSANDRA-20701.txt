Materialized view should automatically SELECT view's primary key columns
Datastax's documentation for CREATE MATERIALIZED VIEW [https://docs.datastax.com/en/cql-oss/3.3/cql/cql_reference/cqlCreateMaterializedView.html] describes the "SELECT" clause as:

*Comma separated list of non-PRIMARY KEY columns from the base table to include in the materialized view. All primary key columns are automatically included.*

In my experiments, I discovered that this behavior was true in Cassandra 3, where all PRIMARY KEY columns of the view were indeed automatically selected, but in Cassandra 4 and 5 this is no longer true, and one must explicitly select all primary key columns as well.

I feel that the new behavior is counter-intuitive and confusing, and wonder whether this was an accidental regression that should be fixed - or was it changed deliberately (why?)

As an example, consider a base table with primary key (p,c) and additional regular columns v1,v2,v3 and then we create a view with:

 
{code:java}
CREATE MATERIALIZED VIEW mv AS 
    SELECT v2 FROM tbl 
    WHERE v1 is not null and p is not null and c is not null 
    PRIMARY KEY (v1, p, c){code}
 

The intention in writing "SELECT v2" was to make v2 the only regular column in the view - the regular column v3 is deliberately not selected, and v1, which was a regular column in the base, is now a primary key column in the view.

This command worked in Cassandra 3 and did the expected thing. However, it no longer works on Cassandra 4 (or 5). It gives the following error message:

 
{code:java}
Unknown column 'v1' referenced in PRIMARY KEY for materialized view 'mv'
{code}
This error message was very confusing for me - why is v1 in the above CREATE MATERIALIZED VIEW an unknown column? I had to think hard before I realized that what this message was trying to tell me was that the PRIMARY KEY clause didn't know what v1 was because I the SELECT it in the same instruction didn't list it.

I wonder if this change in behavior is an unintended regression (which is why I'm reporting it as a bug), or if it was changed intentionally. Cassandra's open-source documentation, [https://cassandra.apache.org/doc/5.0/cassandra/developing/cql/cql_singlefile.html#createMVStmt] - doesn't seem to address this issue at all.

If this change was intentional, perhaps the error message could be clarified? The error could say not that 'v1' is an "unknown column" but that it is unselected, or missing in the SELECT clause, or something to that effect.
