DNS Resolver returns same IP address for 2 different instances
<!-- Please answer these questions before submitting a bug report. -->

### What version of gRPC-Java are you using?
1.60.2

### What is your environment?
<!-- operating system (Linux, Windows,...) and version, jdk version, etc. -->
Linux Alpine with Eclipse Temurin JDK 11. I use Docker to create 3 containers with my application.
We also reproduce the issue with Azure and AWS deployments. They use Ubuntu instead of Alpine.

Every instance creates 2 RPC Clients (one for every of the other instances it has to talk to) that uses 4 stubs (2 blocking, 1 async and 1 future). With the client initialization it creates 1 long lived channel shared by all of the stubs.

Every instance creates a server that listens for request at certain address using the NettyServerBuilder.forAddress()

### What did you expect to see?
I use the deployment to stress test the application. The test restarts some of the containers. 
What I expect is after the restart the instance that is not restarted to be able to send messages to the restarted instances through the already instantiated channels.

### What did you see instead?
Sometimes instance that is not restarted starts sending 2 messages to the same node instead of 1 to each of them.
An interesting detail is that if I shutdown the channel and initialize a new one everything starts working again.

What I have tried so far:
- I turned off the dns cache. That did not fix the issue.
- I created interceptor that sign every request with its recipient and another one that throws exception if the message has a wrong recipient. This way I know when to reinitialize the channel. This is more of a workaround rather than a solution. It adds unnecessary complexity and it is not very stable.

### Steps to reproduce the bug
Not 100% sure if restarting the containers is what causes the issue and it does not reproduce every single time, but from what I see It often happens after some of the containers are restarted.

The logs bellow show that the instance is trying to send messages to the other two that are currently unavailable. Somehow the addresses are the same for the two instances (172.20.0.7:7300)
