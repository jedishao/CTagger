Use distinct semantics for functions that do distincting
Use distinct rather than equals for functions that do distincting.  Currently using these functions on complex types (rows, arrays, maps) with null elements will result in an exception like "ARRAY comparison not supported for arrays with null elements" or  "ROW comparison not supported for fields with null elements".  However, these functions are really doing "distincts" and should match the group by or distinct semantics to be more internally coherent and prevent undesired user query failures.

 I don't think we need to change map functions (e.g. map_agg, multimap_agg) to use distinct semantics because indeterminate map keys (nulls or complex types containing nulls) are not allowed. 

Note: For any changes in Presto java we need to have corresponding changes in Prestissimo/velox to ensure consistent behavior.

Functions include:

- [x] set_agg -- needs changes in velox. currently velox is even more strict than presto about nulls in the input
- [x] set_union -- already has these semantics in velox  
- [x] array_distinct -- not yet implemented in velox for complex types
- [x] array_intersect -- not yet implemeted in velox for complex types
- [x] array_union -- already has these semantics in velox
- [x] array_except -- not yet implemented in velox for complex types
- [ ] arrays_overlap -- not yet implemented in velox for complex types

The following functions need changes, but are sql functions that at some point transform the array values to a map. These will fail with error due to null map keys rather than invalid row/array comparizon. They cannot be fixed without changing the underlying sql function not to use maps or implementing them directly instead of as sql functions
- [ ] array_duplicates -- not yet implemented in velox for complex types
- [ ] array_has_duplicates -- not yet implemented in velox for complex types
- [ ] array_least_frequent -- not yet implemented in velox for complex types

## Expected Behavior or Use Case

The expected behavior is that these functions should behave similar to group by so that ROW(1,null) would be considered the same as ROW(1,null) for all of these functions. As an example:

`array_distinct(array[ROW(1, null), ROW(1,null)])  -- array[ROW(1,null)]`

Examples of current behavior

```

Prestisssimo:
presto:default> SELECT set_union(x) from (VALUES (ARRAY[ row(null, 2)], 2), (ARRAY[row(null, 2)], 3))t(x, y);
```

## Context
Currently users get errors when performing executing these functions on complex types (e.g. rows) containing null values.  We should instead compare with distinct semantics so that nulls are considered not distinct from itself.
