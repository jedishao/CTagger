Trino User Mapping with Apache Ranger Impersonation Fails Due to Principal and User Mismatch
### Description
When configuring Trino to use Apache Ranger for access control and OAuth2 for authentication, there is an issue with user impersonation. Specifically, the Trino principal (derived from the OAuth2 email) cannot impersonate the Trino user (derived from the OAuth2 email after applying a user mapping pattern), resulting in an error.

### Expected Behavior
- Trino should allow the principal myname@example.com (extracted from OAuth2 email) to impersonate the user myname (derived from the user mapping pattern) when Ranger permissions are set to allow {USER} to impersonate {USER}.
- The authenticated user myname should be used to check permissions in Ranger.

### Actual Behavior
When connecting via JDBC with externalAuthentication=true (for OAuth2), Trino returns the following error:
`Access Denied: Principal myname@example.com cannot become user myname`

### Root Cause Analysis
OAuth2 Configuration:
- The OAuth2 principal is extracted from the email address using http-server.authentication.oauth2.principal-field=email.
- Example principal: myname@example.com.
- A user mapping pattern `(.*)(@.*)` is applied to transform the principal into the Trino user.
- Example user: myname.

Ranger Configuration:
- Permissions are set in Ranger to allow the Trino principal {USER} to impersonate the Trino user {USER}.

Issue:
- The Trino principal (myname@example.com) does not match the Trino user (myname) after the user mapping pattern is applied.
- This mismatch causes a conflict with Ranger’s impersonation rule, as the principal is not authorized to impersonate the mapped user.
