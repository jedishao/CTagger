Inefficient queries involving "OR" operator on different columns
We have witnessed this problem using the Iceberg plugin.  The returned rows from those queries are as expected, but a lot more files (splits) are being scanned for nothing since Iceberg metrics are not being leveraged.  We believe this is caused by a bug in `TupleDomain.columnWiseUnion()`.

# How To Reproduce
It is very easy to reproduce the issue by watching the number of splits in the UI while running queries on the following table:
```sql
-- I created that table using SparkSQL
CREATE TABLE
    my_catalog.my_namespace.trino_or_bug TBLPROPERTIES (
        'write.target-file-size-bytes' = '524288', -- Make small files to amplify the problem.
        'write.metadata.metrics.default' = 'none', -- We don't want metrics on every column to show what a full scan does.
        'write.metadata.metrics.column.str_col_1' = 'truncate(16)', -- Iceberg metric default
        'write.metadata.metrics.column.str_col_2' = 'truncate(16)', -- Iceberg metric default
        'write.metadata.metrics.column.int_col_1' = 'truncate(16)', -- Iceberg metric default
        'write.metadata.metrics.column.int_col_2' = 'truncate(16)', -- Iceberg metric default
        'write.metadata.metrics.column.ts_col_1' = 'truncate(16)',  -- Iceberg metric default
        'write.metadata.metrics.column.ts_col_2' = 'truncate(16)'   -- Iceberg metric default
    ) 
    USING iceberg 
AS
SELECT
    'str_1' AS str_col_1,
    'str_2' AS str_col_2,
    'str_3' AS str_col_3,
    1 AS int_col_1,
    2 AS int_col_2,
    3 AS int_col_3,
    TO_TIMESTAMP('2025-06-01 00:00:00') AS ts_col_1,
    TO_TIMESTAMP('2025-06-02 00:00:00') AS ts_col_2,
    TO_TIMESTAMP('2025-06-03 00:00:00') AS ts_col_3
FROM
    range(100 * 1000 * 1000)  -- Create many rows to amplify the problem in Trino UI
```
We have static values for each column, and we have 3 different data types to show the problem is not type-dependent.  The 3rd column of each type do not have metrics to force Trino into a full table scan when those columns are queried.

While monitoring the Trino UI, run the following query:
```sql
select count(*) from my_catalog.my_namespace.trino_or_bug
where int_col_1 = -1;
```
The number of completed splits should be very small (18 for me).

Do the same for `int_col_2`:
```sql
select count(*) from my_catalog.my_namespace.trino_or_bug
where int_col_2 = -2;
```
The number of completed splits should be the same as the first query (18 again for me).

It would be fair to assume that running a query on both columns would not return more splits than adding the splits from both queries:
```sql
select count(*) from my_catalog.my_namespace.trino_or_bug
where int_col_1 = -1 or int_col_2 = -2;
```
but on my machine, I see 11,129 splits!  And the query takes much more time to execute (400ms versus 5s)

If you run a query on `int_col_3`, you get the same number of splits (11,129):
```sql
select count(*) from my_catalog.my_namespace.trino_or_bug
where int_col_3 = -1;
```
In this case, it is expected since Trino cannot leverage Iceberg metrics, so every file will be scanned.
Note that the same behavior happens if you query the string or timestamp columns.

# Possible Root Cause
While debugging the issue, I narrowed it down to `TupleDomain.columnWiseUnion()`.  I might be wrong here, so you guys can tell me.  When debugging, `TupleDomain.columnWiseUnion()` would return `TupleDomain.ALL` since there are no common column names between both predicates (`int_col_1 = -1` and `int_col_2 = -2`).  Returning `TupleDomain.ALL` will make Trino scan every file (split) instead of pruning all files if it would look at Iceberg metrics.  To test this theory, I have modified `TupleDomain.columnWiseUnion()` so that it returns the original `tupleDomains` as a `Map` when the result of the column-wise union is empty.  With that code in place, Trino did not have to scan every split.

I do not have a complete understanding of the entire Trino codebase, so I might be missing something here.  I looked at existing unit tests and found some in `TestTupleDomain.java`.  The following new unit test will fail with the current codebase (we get `TupleDomain.ALL`):
```java
    @Test
    public void testDisjointColumnWiseUnion()
    {
        TupleDomain<ColumnHandle> tupleDomain1 = TupleDomain.withColumnDomains(
                ImmutableMap.<ColumnHandle, Domain>builder()
                        .put(C, Domain.singleValue(BIGINT, 1L))
                        .buildOrThrow());

        TupleDomain<ColumnHandle> tupleDomain2 = TupleDomain.withColumnDomains(
                ImmutableMap.<ColumnHandle, Domain>builder()
                        .put(D, Domain.singleValue(BIGINT, 2L))
                        .buildOrThrow());

        TupleDomain<ColumnHandle> expectedTupleDomain = TupleDomain.withColumnDomains(
                ImmutableMap.<ColumnHandle, Domain>builder()
                        .put(C, Domain.singleValue(BIGINT, 1L))
                        .put(D, Domain.singleValue(BIGINT, 2L))
                        .buildOrThrow());

                        
        assertThat(columnWiseUnion(tupleDomain1, tupleDomain2)).isEqualTo(expectedTupleDomain);
    }
```

We think that there is an edge-case here that is not handled when a query involves an `OR` operator on disjoint column names.
