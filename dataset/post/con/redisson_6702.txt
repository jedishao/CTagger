Significant Performance Regression in Lock Operations After Upgrading from 3.45.1 to 3.46.0
### Redis version

7.4.0

### Redisson version

3.45.1 vs 3.46.0/3.50.0

### Redisson configuration

### Environment

- Redisson versions tested: 3.45.1 vs 3.46.0/3.50.0
- Java version: 17.0.2
- Redis version: 7.4.0
- Redis setup: Master-Slave configuration with replicas

### Redisson Client
```
    @Bean(destroyMethod = "shutdown")
    RedissonClient redisson() {
        Config config = new Config();
        config.setLockWatchdogTimeout(30000)
                .useReplicatedServers()
                .setScanInterval(2000)
                .addNodeAddress(nodesAddress)
                .setReadMode(ReadMode.MASTER)
                .setPassword(password);

        return Redisson.create(config);
    }
```

### What is the Expected behavior?

Lock operations should maintain similar performance characteristics as in version 3.45.1, or at least not show such a dramatic regression.

### What is the Actual behavior?

Lock acquisition and release operations are significantly slower, causing performance bottlenecks in applications that rely heavily on distributed locking.

### Additional information

### Description
After upgrading Redisson from version 3.45.1 to 3.46.0, we observed a significant performance degradation in Redis lock operations. The time required to acquire and release locks has increased dramatically, impacting our application's overall performance.

### Issue Details
The performance regression is particularly noticeable in Master-Slave Redis configurations and affects:

- Lock acquisition time: Increased from ~0.21s to ~0.63s (3x slower)
- Lock release time: Increased from ~0.05s to ~0.81s (16x slower)
- Total operation time: Increased from ~0.38s to ~1.55s (4x slower)

**Important:** This issue appears to be specific to Redis Master-Slave setups with replicas. The performance degradation may not occur in single-node Redis configurations.

### Reproduction Steps
To demonstrate this issue, I created a simple test project that performs basic operations on a Redis-stored object:

1. Acquire a distributed lock
2. Get a bucket from Redis
3. Retrieve an object from the bucket
4. Update the object's UUID
5. Save the updated object back to Redis
6. Release the lock

### Impact Analysis

- getLock operation: ~3x slower (0.21s → 0.63s)
- unlock operation: ~16x slower (0.05s → 0.81s)
- Total execution time: ~4x slower (0.38s → 1.55s)

### Additional Information

- The regression appears to be specifically related to lock operations, as other Redis operations (getBucket, getMyObjectDto, setBucket) show minimal performance changes
- This issue is reproducible across multiple test runs
- The test project isolates the problem to basic lock operations with simple object manipulation
- **Critical:** The performance regression only occurs when using Redis in Master-Slave configuration with replicas
- Single-node Redis configurations may not exhibit this performance degradation
