Coordinator OOM when a query scans many partitions of a Hive table
TupleDomain shows up multiple times in a TableScanNode:

* `.tableLayout.layout.promisedPredicate` (bad; a discrete TupleDomain representing all partitions)
* `.tableLayout.layout.compactEffectivePredicate` (good; compacted [here](https://github.com/prestodb/presto/blob/0.206/presto-hive/src/main/java/com/facebook/presto/hive/HivePartitionManager.java#L167))
* `.currentConstraint` (bad; a discrete TupleDomain representing all partitions)

The `TaskUpdateRequest.fragment` contains the plan of a fragment, which contains the TableScanNode. It is transmitted to each task once.

Due to the **two** bad JSONs in the TableScan node, such a plan would be roughly 8.4MB.

Take a query with 16 scans of a table with 10000 partitions (without any partition filter) in a cluster of 500 workers. It takes up 8.4MB/JSON * 1 JSON/task * 500 workers * 16 stages = 70GB

70GB of JSON is generated in short succession, and handed to Jetty client, which provides little back pressure. This translates into many humongous allocations, and causes significant GC pressure. This could also fill up the heap, leading to OOM.

### `.currentConstraint`

Fix is easy. It is only used during planning, and does not need to be transported to workers. #11133

### `.layout.connectorHandle.promisedPredicate`

This is used in `getOrComputePartitions`, and is need for executing delete on Hive.

The cause has to do with iterative optimization. Let's take a look at [`PickTableLayout.planTableScan`](https://github.com/prestodb/presto/blob/0.206/presto-main/src/main/java/com/facebook/presto/sql/planner/iterative/rule/PickTableLayout.java#L190)

* The first time it's called
  * `predicate` represents the user-provided predicate in the query. (In general, it represents the predicate from filters above.)
  * `node.currentConstraint` is `true`
  * The deterministic part of `predicate` is decomposed into a `TupleDomain` and an expression representing the remaining expression.
    * The expression representing the remaining expression is thrown out. (Is this a bug?)
    * The intersection of the `TupleDomain` and `node.currentConstraint` is stored in `simplifiedConstraint`. (I don't get what `simplified` is supposed to mean here.)
  * `HiveMetadata.getLayouts` is invoked with `simplifiedConstraint`. It returns a `TableLayoutResult`. 
  * For the purpose of this discussion, `TableLayoutResult` consists of roughly 3 parts: (1) `layout.predicate` (2) `unenforcedConstraint` (3) `layout.handle.promisedPredicate` (4) rest of `layout.handle`.
    * What `1` and `3` represents is not documented. Based on my understanding. They need to satisfy the following requirements. Take Universe = `{all tuples of partition column values in the table}`,
      * ~~`1 ∧ 2` must be equal to `simplifiedConstraint`~~ (This is incorrect)
      * ~~`1` must be equal to the list of partitions `4` physically represents.~~ (This is incorrect)
      * `3 ∧ 2` must be equal to `simplifiedConstraint`
      * `3` must be equal to the list of partitions `4` physically represents.
    * In the current implementation, `1` is implemented by reversing from `4`. This makes it a discrete TupleDomain. [here](https://github.com/prestodb/presto/blob/0.206/presto-hive/src/main/java/com/facebook/presto/hive/HiveMetadata.java#L1407)
    * In the current implementation, `3` is implemented by decomposing `simplifiedConstraint`. i.e. [here](https://github.com/prestodb/presto/blob/0.206/presto-hive/src/main/java/com/facebook/presto/hive/HiveMetadata.java#L1367) and [here](https://github.com/prestodb/presto/blob/0.206/presto-hive/src/main/java/com/facebook/presto/hive/HivePartitionManager.java#L154)
  * In the new `TableScanNode`, `node.currentConstraint` will be set to intersect of `1` and `simplifiedConstraint`, making it discrete.
    * Side question: why is the intersection with `simplifiedPredicate` necessary?
* In subsequent times it's called
  * `node.currentConstraint` is now discrete
  * This make `simplifiedConstraint` discrete
  * This then makes `3` discrete

I'm proposing to compute `1` by decomposing `simplifiedConstraint`, instead of by reversing from `4`. This will make it equivalent to `3`.
