Possible memory leaks on selecting certain columns
Hello, all
I have been using presto for 2 years, and really satisfied with it.
I mainly bring up the cluster using EMR and recently upgraded from 0.170 to 0.194 where I think found a bug. 

I have data on s3 that is partitioned by dates that I have it available on presto as external table using hive catalog. The table has about 8 columns all string types, and I am experiencing very weird OOM happening when I query a certain column from it.

> select problematic_column From db.tableA where other_column='abcde' and reqdate='2018-03-01' limit 1;

Above query will run for couple minutes and will fail with OOM. 
(Above query is expect to result 0 rows)
What makes me to think the weird part is 

> select some_other_column From db.tableA where other_column='abcde' and reqdate='2018-03-01' limit 1;

Will run fine with expected result. I checked if there was any problem with problematic column using spark, checking length, any outstanding row, etc. but the column looks alright.

> select problematic_column From b.tableA where reqdate='2018-03-01' limit 1;

Above query ran fine. so it has to do something with worker node has some kind of memory leaking when it has where caluse with condition that will have 0 rows of output. 

When query fails, it actually brings down the worker node with it. When I observed memory usage by presto on worker nodes, when query is running, it will indefinitely use memory until it reaches Xmx on jvm config and worker nodes gets restarted. 

My team has been blocked by this bug and could not use any newer versions of Presto with Disk Spilling avaialble. Any help regarding solving, debugging this bug would be very much appreciated.
