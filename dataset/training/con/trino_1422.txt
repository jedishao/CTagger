Output Buffers remain open after ExchangeClient closes
We've seen an issue in production where queries just hang. This happens when left hand side of a join is very small (ie. has < 20 rows). It seems that the issue arises because of unclosed output buffers. Sharing some investigation here for further discussion. @dain @findepi   

A task can finish successfully only after the output buffers have been completely read by tasks (corresponding to buffers) in the reader stage. Let's say Stage `S3` is a source for Stage `S1`. Also, tasks in `S3` have partitioned output buffers. A task `S3.j` finishes when all tasks in `S1` have completely read data from corresponding output buffers of `S3.j`.

If a task `S1.i` finishes before at least one task in `S3` (say `S3.j`) has been scheduled, the `buffer[i]` in `S3.j` will remain in FLUSHING state and `S3.j` will remain in `RUNNING` state. This is because the reader task `S1.i` is not there to read data from the buffer. And, there is no mechanism that closes such "abandoned" buffers.

Now, the data  in `buffer[i]` of `S3.j` eventually fills the output buffer of completely (i.e. reaches `sink.max-buffer-size` value), since it is not being read. This causes `S3.j` to NOT be able to produce data for other buffer partitions (say `buffer[k]` or `buffer[m]`). And that ends up blocking tasks `S1.k` and `S1.m` because they don't have data to process. This causes the query to completely hang.

This bug depends on the race happenning among (1) scheduling of tasks, (2) finishing of tasks and (3) driver executions within a task. The bug occurs on production clusters undeterminstically.    

I reproduced this deterministically as a unit test on version 203 here: https://github.com/phd3/presto/commit/b542f9751c92df701d4bafb36b49a7d535a82ba5 (need to put more work if we want to check it in after the fix). The `testRaceCondition` class in this commit contains the test. In the reproduced example, `S1` is a Join Stage and `S3` is a buid stage.

![image](https://user-images.githubusercontent.com/6829746/64058653-06ee6b80-cb63-11e9-96f7-69fad22a6719.png)

The code uses a custom scheduler to schedule the stages and tasks in a certain order. Key requirements that enable reproducing the bug reliably are as follows:

* Stage `S1` contains a distributed hash join (inner) between two stages `S2` (probe) and `S3` (build). `S2` and `S3` both have tablescans. All the stages will have two tasks. `task.concurrency` is set to 1, which means there will be one driver per pipeline in every task.

* Output from `S2` will only be a single row. This means that at least one task in `S1` is going to have zero rows on the probe side. Having at least one task with no probe input rows is crucial for the bug's reproduction. Output from `S3` should be bigger. 

* Desired order of execution:
1. Stage `S2` is scheduled (that launches `S2.0` and `S2.1`)
2. All the output buffers in stage `S2` are in FLUSHING state (The data is so small that everything fits in the buffer, even without anyone reading)
3. Stage `S1` is scheduled, launching `S1.0` and `S1.1`. There are 3 pipelines here: (P1) build side exchange (ExchangeOperator->LocalExchangeSinkOperator) (P2) Hash building (LocalExchangeSourceOperator->HashBuilderOperator) (P3) Probe side Exchange and LookupJoin (ExchangeOperator->LookupJoinOperator->TaskOutputOperator) 
4. Let's say probe input for task `S1.0` is 0 rows. pipeline `P1` in task `S1.0` starts executing, and finishes immediately, finishing all operators since there is no data. `P2` and `P3` in `S1.0` are blocked on `LocalExchangeSourceOperator` and `ExchangeOperator` respectively. For `S1.1`, all pipelines are blocked.
5. Only one task from stage `S3` is scheduled, say `S3.0`.
6. This causes `P2` and `P3` from `S1.0` to be unblocked, and finishes both of them. Task `S1.0` finishes. 
7. `S3.1` is scheduled, and begins scanning a bigger table. It has a partitioned output buffer with two partitions buffer[0] (for `S1.0`) and buffer[1] (for `S1.1`). The example uses max buffer size of 1MB, which is considered in an aggregate sense, not separately accounted for individual partitions. buffer[0] keeps filling until 1MB limit is reached. It blocks any data from being produced in for buffer[1]. So now `S1.1` remains blocked, waiting for data. And the query hangs.

Tried reproducing this in version 317 also, but this particular example bug doesn't work. The execution goes the same way until step 6 above. At this point, P2 does not finish like it did in version 203. This essentially means that the join execution is still waiting for the hash to be built completely, when it knows that all the probe operators have already finished.

I believe that the issue of output buffers not being closed is _still_ there in 317. 
But it is circumvented for this example since the short-circuting in the join (as mentioned here) does not happen anymore. Is that true? I believe that the change was introduced in https://github.com/prestodb/presto/pull/11636. `lookupSourceProviderFuture` needs to be set when we close the `LookupJoinOperator` so that `whenAllFinishes` gets unblocked and triggers `joinBridge::destroy`. That will short-circuit the join by shutting down HashBuilderOperator. short-circuiting will also bring the join hang issue back.

Coming back to the original issue, we need to close such abandoned buffers to enable more short-circuiting. This PR https://github.com/prestodb/presto/pull/10604 attempted to do this. @dain mentioned that this was reverted because it results in too many HTTP requests, and that we need to do this in batch. @dain @findepi please share your thoughts and more context on this if any.
